# App Store 4.3 整改

目标是让应用在产品能力、交互和代码组织上形成可审核的实质差异，并在用户授权的项目范围内完成重构。架构变化本身不能保证通过审核；不要把改目录、改命名、换颜色、替换图标或增加无业务价值的包装视为 4.3 的充分整改，也不要承诺审核结果。

## 优先级

1. 用户已经指定 A、B、C、D、E 中的方案或明确架构时，直接采用该方案，不再替用户改选；先读取对应 reference，再结合项目实际实施。
2. 用户没有指定方案，但明确了改造幅度时，按该幅度和项目兼容性选择。
3. 关键信息缺失且不同答案会显著改变方案或造成数据迁移风险时，可以简短询问；否则先检查项目并作出可逆、合理的选择。

可询问的关键信息包括：

- 希望小改、中等改造还是大改？大改默认选择可兼容的最高复杂度方案；小改优先控制迁移范围，但必须包含足以形成实质差异的产品与交互改造。
- 是否必须保留现有最低系统版本、第三方依赖政策、本地数据及其兼容性？
- 审核原文是什么，同一开发者账号下是否有功能、素材或二进制高度相似的其他应用？

若用户只说“尽量少改”，不要选择近乎没有变化的做法。说明最小可行整改边界，并实施能解决重复性问题的最小完整方案。

## 先检查再选方案

阅读项目说明和适用的 `AGENTS.md`，检查工程类型、最低系统版本、SwiftUI/UIKit、当前架构、依赖、持久化、导航、核心功能、测试、未提交改动，以及可见的 4.3 相似风险。区分：

- 产品层：核心用途、目标用户、功能闭环、内容/数据来源是否与已有应用实质重复。
- 体验层：信息架构、主要流程、页面结构和交互是否只是换皮。
- 工程层：模块边界、状态管理、数据层、模型和命名是否高度复用。

选择方案时同时考虑整改强度、迁移成本和技术兼容性：

- [方案 B](references/Solution%20B.md)：MVC + UserDefaults/Plist，复杂度与工程迁移成本最低。适合小型、轻量数据项目的小改；仍须重做至少一条核心用户流程并提供真实差异化能力，不能只移动文件或套用 Controller。
- [方案 A](references/Solution%20A.md)：MVVM + CoreData，中等复杂度。适合现有 SwiftUI/MVVM、需要结构化本地数据，或希望中等改造且保持原生依赖的项目。
- [方案 D](references/Solution%20D.md)：Clean Architecture + JSON，较高复杂度。适合需要明显分层、保持纯原生依赖或最低系统版本不适合 SwiftData 的中大型改造。
- [方案 E](references/Solution%20E.md)：TCA + UserDefaults，较高复杂度和依赖迁移成本。优先用于已有 TCA/单向数据流基础，或用户明确接受引入 Composable Architecture 的项目；不要仅为提高复杂度强加第三方依赖。
- [方案 C](references/Solution%20C.md)：VIPER + SwiftData，默认视为最高结构改造量。大改且项目可采用 iOS 17+/SwiftData 时优先；若最低系统版本或数据兼容要求不允许，选 D，或在用户已指定 C 时先说明并解决兼容约束。

选择前只需完整读取最匹配方案的 reference；若在两个方案之间权衡，再读取这两个。reference 是架构蓝图而非必须逐字复制的模板：保留项目真实领域命名和可工作的既有能力，不引入示例中的 `Item`、占位 API、项目名或无业务意义的文件。

## 制定整改范围

把 4.3 整改拆成一个可验证的最小完整切片，至少覆盖：

- 一项有真实用户价值的差异化核心能力，或对现有核心能力的实质深化。
- 与该能力匹配的主流程、页面状态、导航和空白/错误状态，而非单纯视觉换肤。
- 所选方案要求的状态、领域/业务和存储边界；只迁移被改流程及其共享依赖，除非用户选择大改或指定全量重构。
- 必要的数据迁移或向后兼容，避免已有用户数据静默丢失。
- 可用于审核说明的客观变更摘要和复现路径。

如果仅凭仓库无法判断“与哪些应用重复”，不要虚构竞品或审核原因；先完成仓库内可证实的诊断，并明确还需要审核原文或相似应用信息才能判断的部分。

## 实施

1. 在修改前记录选择的方案、选择理由、预计改造范围和主要风险；若用户已选方案，只说明如何适配项目。
2. 先建立所选架构的边界和依赖方向，再迁移一条端到端核心流程，确保每一步保持可构建；随后扩展到约定范围。
3. 尽量复用稳定的领域逻辑与资源，但重写造成同质化的产品流程和表现层。不要为了“看起来改得多”复制无用样板、批量改名或破坏现有功能。
4. 添加或更新与改造相称的测试，重点覆盖新能力、状态转换、持久化/迁移及失败路径。
5. 遵守仓库现有约束并保护用户未提交的改动，不修改任务无关内容。

## 验证与交付

运行项目已有的格式检查、静态检查、测试和构建。使用 Xcode 编译时，若 5 分钟仍未返回结果，立即取消编译，继续能执行的验证，并明确告知用户该次编译失败。不得把超时描述为通过。

交付时简要说明：采用的方案及原因、完成的产品与架构变化、数据兼容处理、验证结果、仍存在的审核风险，以及可供 App Review 复现新能力的步骤。把通过 4.3 表述为降低风险，不作保证；若仍只有架构变化而缺少可辨识的产品差异，应明确指出整改尚不充分。
